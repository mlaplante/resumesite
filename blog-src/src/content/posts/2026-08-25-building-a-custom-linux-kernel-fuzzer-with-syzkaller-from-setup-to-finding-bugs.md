# Building a Custom Linux Kernel Fuzzer with Syzkaller: From Setup to Finding Bugs

As an SVP of Information Security and Operations, I've seen firsthand how critical robust security testing is for the foundational components of our infrastructure. The Linux kernel, being at the heart of nearly everything we do, is a prime target for attackers. While manual code review and static analysis are invaluable, they often fall short in uncovering subtle, complex bugs that only manifest under specific, unexpected execution paths. This is where fuzzing shines, and specifically, where tools like Syzkaller become indispensable.

Syzkaller is a powerful, open-source kernel fuzzer developed by Google. It's designed to find bugs in operating system kernels by generating sequences of system calls, executing them, and monitoring for crashes, hangs, or other anomalous behavior. While Syzkaller comes with excellent support for common Linux distributions, there are times when you need to target a very specific, perhaps custom-built, kernel or a particular subsystem that isn't covered by its default syzkaller descriptions. This post will walk you through setting up a custom Syzkaller environment to fuzz a specific Linux kernel, from compilation to finding your first bug.

## Understanding the Syzkaller Architecture

Before we dive into the setup, let's briefly understand how Syzkaller operates. It consists of several components:

*   **`syz-manager`**: The central orchestrator. It manages virtual machines (VMs), compiles fuzzing programs, collects crash reports, and performs various other administrative tasks.
*   **`syz-fuzzer`**: Runs inside the guest VM. It generates and executes system call sequences, communicating with `syz-manager` to send back coverage information and crash reports.
*   **`syz-executor`**: A small C program compiled into the kernel image. It executes the system call programs generated by `syz-fuzzer` and captures coverage.
*   **`syz-extract`**: Extracts system call information from kernel headers.
*   **`syz-sysgen`**: Generates C and Go code for system call descriptions.

## Step 1: Preparing Your Custom Linux Kernel

The first step is to prepare the Linux kernel you intend to fuzz. Syzkaller requires specific kernel configurations to enable coverage collection, KASAN (Kernel Address Sanitizer), KCSAN (Kernel Concurrency Sanitizer), and other debug features that help pinpoint bugs.

Let's assume you're working with a custom kernel source tree. Here's a minimal set of configuration options you'll need. You can typically add these to your existing `.config` file or enable them via `make menuconfig`.

```
# General debug options
CONFIG_KASAN=y
CONFIG_KASAN_GENERIC=y
CONFIG_KASAN_OUTLINE=y
CONFIG_KCSAN=y
CONFIG_KCOV=y
CONFIG_DEBUG_INFO=y
CONFIG_DEBUG_INFO_DWARF5=y
CONFIG_DEBUG_KMEMLEAK=y
CONFIG_LOCKUP_DETECTOR=y
CONFIG_PROVE_LOCKING=y
CONFIG_BUG_ON_DATA_CORRUPTION=y

# Syzkaller specific options
CONFIG_KCOV_INSTRUMENT_ALL=y
CONFIG_KCOV_ENABLE_COMPARISONS=y
CONFIG_DEBUG_SYSCALL=y
CONFIG_KALLSYMS=y
CONFIG_KALLSYMS_ALL=y
CONFIG_SLUB_DEBUG=y
CONFIG_FAULT_INJECTION=y
CONFIG_FAULT_INJECTION_DEBUG_FS=y
CONFIG_RETHINKDB_DEBUG=y # Placeholder, ensure your actual debug options are enabled

# Networking (often needed for syscalls)
CONFIG_NET=y
CONFIG_INET=y
CONFIG_IPV6=y
CONFIG_UNIX=y
CONFIG_PACKET=y

# Filesystem (for various syscalls)
CONFIG_EXT4_FS=y
CONFIG_TMPFS=y
```

**Actionable Takeaway:** Always start with a `defconfig` for your architecture (e.g., `make x86_64_defconfig`) and then layer these debug configurations on top. This ensures you have a baseline of necessary drivers and features.

After configuring, compile your kernel:

```bash
make -j$(nproc) bzImage modules
make -j$(nproc) headers_install # Important for syz-extract
```

Keep track of the `bzImage` path and the kernel source directory; you'll need them later.

## Step 2: Setting Up the Syzkaller Environment

Now, let's set up the Syzkaller toolchain.

### Install Dependencies

First, ensure you have the necessary build tools:

```bash
sudo apt update
sudo apt install git make gcc clang lld golang-go python3 python3-pip debootstrap qemu-system-x86 bridge-utils tunctl libvirt-daemon-system libvirt-clients
```

### Build Syzkaller

Clone the Syzkaller repository and build it:

```bash
git clone https://github.com/google/syzkaller.git
cd syzkaller
make
```

This will build all Syzkaller components (e.g., `syz-manager`, `syz-fuzzer`, `syz-executor`) in the `bin/` directory.

### Create a Disk Image for the Guest VM

Syzkaller needs a root filesystem for the guest VM. We'll create a minimal Debian-based image.

```bash
# Create a directory for the image
mkdir -p workdir/debootstrap
cd workdir/debootstrap

# Bootstrap a minimal Debian system
sudo debootstrap --arch=amd64 sid ./debian-sid/ http://deb.debian.org/debian/

# Create a disk image
dd if=/dev/zero of=disk.img bs=1M count=2048
sudo mkfs.ext4 disk.img

# Mount the image and copy the bootstrapped system
mkdir mnt
sudo mount -o loop disk.img mnt
sudo cp -a ./debian-sid/* mnt/
sudo umount mnt

# Install necessary packages inside the image (via chroot or directly)
# For simplicity, let's use a temporary mount and copy
# You'd typically chroot to install ssh, etc.
# For Syzkaller's internal communication, ssh isn't strictly necessary if using virtio-vsock,
# but it's good for debugging.

# Minimal setup for Syzkaller:
# Create /etc/fstab for proper boot
echo "rootfs / rootfs rw 0 0" | sudo tee -a mnt/etc/fstab
echo "proc /proc proc rw,nosuid,nodev,noexec,relatime 0 0" | sudo tee -a mnt/etc/fstab
echo "sysfs /sys sysfs rw,nosuid,nodev,noexec,relatime 0 0" | sudo tee -a mnt/etc/fstab
echo "devtmpfs /dev devtmpfs rw,nosuid,size=65536k,nr_inodes=262144,mode=755 0 0" | sudo tee -a mnt/etc/fstab

# Create a user for Syzkaller if needed (syzkaller user is typically used)
# This is usually done by syz-manager if using SSH, but for minimal setup,
# ensure a 'syzkaller' user exists, or configure syzkaller to use root.
# For simplicity, we'll assume root for now.
```

**Actionable Takeaway:** For a production fuzzing setup, consider using a pre-built Syzkaller image or a more robust image creation script that includes SSH for easier debugging into the guest VM. The `create-image.sh` script in `syzkaller/tools` is an excellent starting point.

## Step 3: Configuring Syzkaller for Your Custom Kernel

Now, we need to tell Syzkaller about our custom kernel and setup. This is done via a JSON configuration file.

Create a file named `my_custom_config.json` in your `syzkaller` directory:

```json
{
    "target": "linux/amd64",
    "http": ":8000",
    "workdir": "/path/to/syzkaller/workdir",
    "kernel_obj": "/path/to/your/kernel/source",
    "kernel_src": "/path/to/your/kernel/source",
    "image": "/path/to/syzkaller/workdir/debootstrap/disk.img",
    "sshkey": "/path/to/syzkaller/workdir/debootstrap/ssh_key/id_rsa",
    "syzkaller": "/path/to/syzkaller",
    "procs": 8,
    "type": "qemu",
    "vm": {
        "count": 4,
        "kernel": "/path/to/your/kernel/source/arch/x86/boot/bzImage",
        "cpu": 2,
        "mem": 2048,
        "cmdline": "root=/dev/sda console=ttyS0 earlyprintk=ttyS0",
        "qemu_args": "-enable-kvm"
    },
    "ignores": [
        "BUG: KASAN: double-free",
        "BUG: KASAN: use-after-free",
        "BUG: KASAN: slab-out-of-bounds"
    ],
    "enable_syscalls": [
        "openat", "read", "write", "close", "mmap", "ioctl", "socket", "bind", "connect", "sendto", "recvfrom", "fork", "execve", "exit"
        // Add more syscalls relevant to the subsystem you want to fuzz
    ]
}
```

**Key configuration parameters:**

*   **`target`**: The architecture of your kernel.
*   **`http`**: Port for the Syzkaller web UI.
*   **`workdir`**: Directory for Syzkaller to store logs, crash reports, and temporary files.
*   **`kernel_obj`**: Path to your *compiled* kernel build directory. This is where Syzkaller finds `vmlinux` for symbolization.
*   **`kernel_src`**: Path to your kernel *source* directory. Used by `syz-extract` for syscall information.
*   **`image`**: Path to the guest VM disk image.
*   **`sshkey`**: Path to an SSH private key for `syz-manager` to connect to the guest.
